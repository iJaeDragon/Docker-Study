# Docker Compose 멀티 컨테이너 실습 레퍼런스 (DB + Backend + Frontend)

> 학습 회차: Docker Compose로 데이터베이스(MariaDB) + 백엔드(Spring Boot) + 프론트엔드(React.js)를 한 번에 관리하기
> 목적: 나중에 비슷한 3-tier 구성을 다시 만들 때 그대로 참고/복붙할 수 있는 수준으로 정리.

---

## 1. 최종 아키텍처

<img width="804" height="341" alt="image" src="https://github.com/user-attachments/assets/8f4ada77-f7e1-4c66-a5f7-5d7b1cd1c922" />

- 브라우저 → `myfrontend`(80) → `mybackend`(8088→8080) → `mydb`(13306→3306)
- 세 서비스 모두 같은 네트워크(`mynetwork`)에 속해있어, 서비스명을 호스트명처럼 사용해 서로 통신한다.
  (예: 백엔드 설정의 DB 접속 주소 = `mydb:3306`, `localhost`가 아님)
- `mydb`는 볼륨(`./data:/var/lib/mysql`)을 사용해 컨테이너를 지워도 데이터가 유지된다.

## 2. 최종 docker-compose.yml 예시 (재구성)

> 원본 강의에서는 예제 2번(DB만) → 3번(DB+Backend) → 4번(DB+Backend+Frontend) 순서로 단계적으로 파일을 늘려갔다.
> 아래는 최종 완성본(4번) 기준으로 재구성한 예시. 실제 사용 시 이미지 태그·경로·비밀번호는 본인 환경에 맞게 수정.

```yaml
version: "3"

services:
  mydb:
    image: mariadb:latest
    container_name: mydb
    environment:
      MYSQL_ROOT_PASSWORD: ""        # 실습용 empty, 운영에서는 반드시 값 지정
      MYSQL_DATABASE: mydb
    ports:
      - "13306:3306"                  # 로컬에 이미 3306(MySQL)이 떠 있는 경우 대비
    volumes:
      - ./data:/var/lib/mysql          # 데이터 영속화 (본인 작업 디렉토리 기준 상대경로)
    networks:
      - mynetwork

  mybackend:
    image: myaccount/my-backend:1.0    # Docker Hub 계정/이미지명은 본인 것으로 교체
    container_name: mybackend
    environment:
      DB_HOST: mydb                    # 서비스명을 호스트명처럼 사용
      DB_PORT: 3306
      DB_NAME: mydb
    ports:
      - "8088:8080"
    depends_on:
      - mydb
    networks:
      - mynetwork

  myfrontend:
    image: myaccount/my-frontend:1.0
    container_name: myfrontend
    ports:
      - "80:80"
    depends_on:
      - mydb
    networks:
      - mynetwork

networks:
  mynetwork:
    external: true                     # 아래 3절 참고: 컴포즈 밖에서 미리 생성해둔 네트워크 사용
```

## 3. 외부(external) 네트워크를 쓰는 이유

`docker-compose down`을 실행하면 Compose가 자동 생성한 네트워크(`{폴더명}_default`)도 함께 삭제된다.
네트워크를 계속 유지하고 싶다면(다른 프로젝트와 공유하거나, down/up을 반복해도 네트워크 설정을 유지하고 싶을 때) **Compose 밖에서 미리 만들어두고 `external: true`로 참조**한다.

```bash
# 최초 1회만 실행 (이미 있으면 에러 발생하니 존재 여부 먼저 확인)
docker network ls | grep mynetwork
docker network create mynetwork

# 확인
docker network ls
docker network inspect mynetwork   # 연결된 컨테이너 목록 확인
```

> `external: true`로 지정한 네트워크는 `docker-compose down`을 해도 삭제되지 않고 남아있다. 이후 `docker network inspect mynetwork`로 확인하면 연결된 컨테이너 목록이 비어있는 상태로 유지된다.

## 4. 실행 순서 문제와 대응법 (depends_on의 한계)

`depends_on`을 걸어놔도 **완전히 준비된 상태를 100% 보장하지 않는다.** 특히 `mybackend`가 `mydb`보다 먼저 완전히 뜨는 순간, DB 연결 실패로 API 응답이 비정상일 수 있다 (에러 로그는 뜨지만 전체 기동이 끝나면 대부분 정상화됨).

### 방법 A — 서비스를 나눠서 순차 실행 (강의에서 실제로 쓴 방법)

```bash
# 1) DB만 먼저 백그라운드로 기동 (완전히 뜰 때까지 기다림)
docker-compose -f docker-compose.yml up -d mydb

# 2) 상태 확인
docker-compose -f docker-compose.yml ps

# 3) 나머지 서비스 기동 → 이미 떠 있는 mydb는 건너뛰고 backend/frontend만 추가로 시작됨
docker-compose -f docker-compose.yml up -d
```

### 방법 B — 이미 오류가 난 경우, DB는 유지한 채 backend만 재기동

```bash
docker-compose -f docker-compose.yml stop mybackend
docker-compose -f docker-compose.yml rm mybackend      # 확인 프롬프트 나오면 y
docker-compose -f docker-compose.yml up -d mybackend
```

이렇게 하면 DB 데이터/연결은 그대로 두고 backend 컨테이너만 새로 만들어서, DB가 이미 준비된 상태에서 재연결하게 되어 오류가 해결된다.

## 5. 로그/상태 확인 명령어

```bash
# Compose 기준 컨테이너 상태 확인
docker-compose -f docker-compose.yml ps

# 전체 로그 (여러 서비스 로그가 섞여서 출력됨)
docker-compose -f docker-compose.yml logs

# 특정 서비스 로그만 필터링해서 확인 (트러블슈팅 시 가장 많이 씀)
docker-compose -f docker-compose.yml logs mydb
docker-compose -f docker-compose.yml logs mybackend

# 실시간 tail (필요시)
docker-compose -f docker-compose.yml logs -f mybackend

# 네트워크에 실제로 어떤 컨테이너들이 연결돼 있는지 확인
docker network inspect mynetwork
```

**정상 동작 확인 방법**
- `mybackend`만 확인: `http://localhost:8088/카탈로그경로` → JSON 응답이 나오면 backend-DB 연결 정상
- 전체 확인: `http://localhost` (80포트 생략 가능) → 프론트엔드 화면에 백엔드에서 가져온 데이터가 테이블 형태로 표시되면 3-tier 전체 정상 작동

## 6. 트러블슈팅 체크리스트

| 증상 | 원인 | 해결 |
|---|---|---|
| `docker network create` 시 이미 존재한다는 에러 | 이전에 이미 만들어둔 네트워크가 있음 | `docker network ls`로 확인 후 생성 스킵, 그대로 사용 |
| 백엔드 로그에 DB 연결 에러 | mydb보다 mybackend가 먼저 뜸 (depends_on 한계) | 4절 방법 A(순차 실행) 또는 방법 B(backend만 재기동) |
| 프론트엔드에서 데이터가 안 보임 | 백엔드 API 자체가 아직 정상화 안 됨 | `logs mybackend`로 에러 확인 → 방법 B로 backend 재기동 |
| `docker-compose rm` 시 "대상 없음" | 먼저 `stop`을 안 하고 바로 `rm` 시도 | `stop` → `rm` 순서로 실행 |
| 포트 충돌로 DB 컨테이너가 안 뜸 | 로컬에 이미 3306 포트를 쓰는 MySQL 등이 실행 중 | `ports`의 호스트 포트를 `13306` 등 다른 값으로 변경 |

---

## 7. 핵심 정리

- 컨테이너가 1개뿐이면 굳이 Compose를 쓸 필요는 없지만, **2개 이상**을 함께 관리해야 한다면 Compose가 로그 관리·명령어 제어 면에서 훨씬 효율적.
- 서비스명이 곧 컨테이너 간 통신용 호스트명이 된다는 점이 핵심 개념.
- 볼륨으로 데이터 영속화, external 네트워크로 네트워크 유지, `depends_on`의 한계와 순차 실행 대응법 — 이 세 가지가 이번 실습에서 가장 실전에서 자주 써먹게 되는 부분.
