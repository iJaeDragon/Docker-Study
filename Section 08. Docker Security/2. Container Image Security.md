# 컨테이너 이미지 보안 — Docker Scout & Trivy 취약점 점검

## 1. 왜 이미지 보안 점검이 필요한가

- 컨테이너 이미지는 Dockerfile의 각 명령어(레이어)로 자유롭게 만들어지고 쉽게 변형된다 → 그만큼 **보안 취약점에 민감**하다.
- 소프트웨어를 자유롭게 추가/변경/실행할 수 있다는 이미지의 유연함이, 동시에 검증되지 않은 위험 요소가 섞여 들어갈 여지이기도 하다.
- 검증 없이 이미지를 사용하다가, 나중에 운영 중인 서비스에 문제가 생기거나 회사 정책상 특정 이미지를 더 이상 못 쓰게 될 수도 있다 → **처음부터 취약점 점검을 거치는 습관**이 중요.

### 이미지 크기와 보안의 관계

- 이미지가 크다 = 더 많은 기능/라이브러리를 포함 = **외부에 노출될 위험 요소도 많아진다.**
- 필요한 최소한만 포함한 경량 이미지를 흔히 **Alpine** 이미지라고 부른다 (이미지 이름에 `alpine`이 들어가면 대체로 사이즈가 작은 버전).

## 2. SBOM과 CVSS 개념

| 용어 | 설명 |
|---|---|
| **SBOM** (Software Bill of Materials) | 소프트웨어 자재 명세서. 알려진 보안 취약점들이 데이터베이스화되어 있고, **지속적으로 업데이트**됨 |
| **CVSS Score** (Common Vulnerability Scoring System) | 취약점의 심각도를 점수로 매긴 공통 기준. 점수가 높을수록 심각(critical) |

스캐너(Docker Scout, Trivy 등)는 **점검 대상 이미지 ↔ SBOM 데이터베이스**를 비교해서 취약점을 찾아내고, 그 결과를 아래 등급으로 분류해서 보여준다.

| 등급 | 의미 |
|---|---|
| **Critical** | 가장 심각, 최우선 조치 필요 |
| **High** | 심각도 높음, 조치 권장 |
| **Medium** | 중간 수준 |
| **Low** | 경미, 즉각 조치 불필요한 경우가 많음 |

> 실무 경험 예시: 금융권 프로젝트에서 **CVSS v2.0 기준**으로 Medium 이상(High, Critical)에 대해 반드시 개선하라는 요구를 받은 사례가 있음 — 업계·회사별로 "어느 등급까지 조치해야 하는가" 기준이 다를 수 있다.

**개선 방법 예시**: 문제 있는 라이브러리를 찾아서 (1) 버전 업그레이드, (2) 다른 라이브러리로 대체, (3) 아예 삭제 — 이후 다시 스캔해서 문제가 해소됐는지 재확인.

## 3. Docker Scout 사용법

- **Docker Desktop에 기본 포함**되어 있음 (Windows/macOS). 리눅스에서 별도 Docker를 설치한 경우엔 Scout를 별도로 설치해야 함 (Docker 공식 사이트의 Scout 설치 안내 참고).

### 3.1 빠른 점검 (Quick View)

```bash
docker scout quickview <이미지명>:<태그>
```

결과 예시 해석: `Critical: 4건, High: 89건, Medium: 198건, Low: 65건` 형태로 등급별 개수가 표시된다.

> 베이스 이미지(예: CentOS 8)에서는 취약점이 적었는데, 그 위에 SSH·Docker 등 여러 패키지를 추가 설치하면서 Critical/High 건수가 크게 늘어나는 경우가 흔하다 — **레이어를 추가할 때마다 위험이 늘어날 수 있다**는 걸 보여주는 사례.

### 3.2 개선 가이드 확인 (Recommendations)

```bash
docker scout recommendations <이미지명>:<태그>
```

취약점을 어떻게 해결하면 좋을지 **대안(다른 버전, 대체 패키지 등)**까지 함께 안내해준다.

### 3.3 도움말

```bash
docker scout --help
```

## 4. Trivy 사용법

- **Aqua Security**사에서 개발한 오픈소스 컨테이너 취약점 스캐너. Docker Scout보다 **더 최신화된 데이터베이스**를 사용하는 경우가 많고, 결과를 표 형태로 깔끔하게 정리해서 보여준다.
- OS 레벨(운영체제 패키지)뿐 아니라 미들웨어, 애플리케이션 라이브러리까지 폭넓게 점검.
- 자체 스토리지에 취약점 DB를 내장하고 있어 별도의 외부 DB 설치가 필요 없음.

### 4.1 Trivy 이미지 받기

```bash
docker pull aquasec/trivy:0.18.3    # 버전은 최신 릴리스에 맞춰 조정
```

### 4.2 Trivy로 이미지 스캔 실행

```bash
docker run --rm \
  -v $HOME/cache:/root/.cache \
  aquasec/trivy:0.18.3 image <점검할 이미지명>:<태그>
```

- 캐시 폴더를 볼륨 마운트해두면 취약점 DB를 매번 새로 받지 않고 재사용 가능.
- 최초 실행 시 DB 다운로드 + 비교 작업 때문에 시간이 걸릴 수 있음.

### 4.3 결과 해석

- 패키지별로 표가 출력되며, **모두 0으로 표시되면 문제 없음**을 의미.
- 문제가 있는 패키지는 **현재 설치된 버전 vs 수정된(패치) 버전**을 함께 보여줘서 바로 업그레이드 방향을 잡을 수 있다.
- 예시: `apt` → Low(조치 불필요), `bash` → High(다른 버전으로 교체 권장) 같은 식으로 패키지별 심각도가 다르게 나옴.

## 5. Docker Scout vs Trivy 비교

| 항목 | Docker Scout | Trivy |
|---|---|---|
| 제공 주체 | Docker(Docker Desktop 기본 포함) | Aqua Security (오픈소스) |
| 설치 | Windows/macOS는 기본 내장, Linux는 별도 설치 | Docker 이미지로 간편하게 pull해서 사용 |
| 특징 | Quick View / Recommendations로 개선 가이드 제공 | 더 최신화된 DB, 표 형태의 깔끔한 리포트, OS+미들웨어+앱 라이브러리까지 폭넓게 점검 |
| 권장 사용법 | **1차 점검**으로 빠르게 훑어보기 | 여유가 있다면 **2차 검증**으로 교차 확인 |

> 두 도구가 사용하는 데이터베이스가 다르기 때문에 **검출 결과(건수)가 서로 다를 수 있다.** 하나만 믿기보다 상황에 따라 교차 검증하는 것이 안전하다.

## 6. CI/CD 파이프라인에 통합하기

이미지 취약점 스캔은 **CI/CD 파이프라인의 한 단계로 넣는 것이 이상적**이다.

```
소스 코드 → 빌드 → 이미지 패키징 → [Trivy/Scout 취약점 스캔] → (문제 없음 확인) → 배포
```

스캔 결과 Critical/High가 발견되면 파이프라인을 **중단시키고 배포를 막는** 방식으로 구성하는 것이 일반적인 실무 패턴.

---

## 7. 핵심 정리 (체크리스트)

- [ ] 이미지는 레이어 구조상 자유롭게 변형되기 쉬워 취약점에 민감하다 — **검증 없이 사용하지 말 것**
- [ ] 이미지 크기는 작을수록 노출 위험이 줄어든다 (Alpine 계열 활용 고려)
- [ ] `docker scout quickview <이미지>`로 Critical/High/Medium/Low 건수 빠르게 확인
- [ ] `docker scout recommendations <이미지>`로 구체적인 개선 방법 확인
- [ ] Trivy는 `docker pull aquasec/trivy` 후 `docker run ... image <이미지>`로 실행, 캐시 볼륨 마운트 권장
- [ ] 두 도구의 결과가 다를 수 있으니 필요시 교차 검증
- [ ] 실무에서는 이미지 취약점 스캔을 **CI/CD 파이프라인 단계로 통합**해 Critical/High 발견 시 배포를 막는 것이 일반적
