# Docker 데몬(엔진) 보안 레퍼런스

## 1. Docker 보안의 4가지 영역

<img width="950" height="281" alt="image" src="https://github.com/user-attachments/assets/d59b3f67-a76e-4960-9c54-cc070531e188" />

| 영역 | 핵심 질문 |
|---|---|
| **① 데몬(엔진) 보안** | Docker 엔진 자체를 얼마나 안전하게 운영하고 있는가? (이번 문서) |
| ② 이미지 보안 | 사용하는 컨테이너 이미지가 안전하다고 검증됐는가? |
| ③ 컨테이너 격리(Isolation) | 컨테이너가 다른 컨테이너/호스트에 영향을 주지 않고 독립적으로 실행되는가? |
| ④ 런타임 보안 | 컨테이너가 실행되는 동안 지속적으로 모니터링/관리되고 있는가? |

이미지가 있어야 컨테이너를 만들 수 있고, 그 컨테이너는 격리된 채로 실행되며, 실행 중(런타임)에는 계속 관리가 필요하다 — 이 전 과정의 기반이 되는 것이 **Docker Daemon**이기 때문에 가장 먼저 다룬다.

---

## 2. Docker Daemon(엔진)이란

- `Docker Daemon`(`dockerd`) = **Docker Engine**. 컨테이너가 실제로 운영될 수 있게 해주는 핵심 프로세스.
- Docker의 구성은 크게 **Client(클라이언트)**와 **Server(데몬)** 두 부분으로 나뉜다.
  - Client: 터미널/CLI에서 `docker run`, `docker ps` 같은 명령어를 입력하는 쪽
  - Daemon(Server): Client의 요청을 **API 형태로 전달받아** 실제 컨테이너를 생성/관리하는 쪽

## 3. 문제점 — Daemon은 보통 루트 권한으로 실행된다

- Docker Desktop(Windows/macOS)을 설치할 때, 대부분 **사용자 계정으로 로그인한 상태**에서 설치하게 되는데 이 계정은 대체로 **루트(관리자) 권한**을 갖고 있다.
- 그 결과 **Docker Daemon 자체가 루트 권한으로 실행**되는 경우가 많다 → 데몬에 대한 접근/제어권을 가진 사람은 사실상 호스트 시스템 전체에 영향을 줄 수 있는 힘을 갖게 된다.
- 리눅스에서는 세분화된 정책 설정이 비교적 쉽지만, **Windows/macOS의 Docker Desktop 환경에서는 이런 제약을 걸기가 상대적으로 불편하고 제한적**이라 더 주의가 필요하다.

---

## 4. 대응 방법 — 루트 계정 사용 제한

| 방법 | 설명 |
|---|---|
| 일반 사용자 계정 사용 | 루트 계정을 직접 쓰지 않고 일반 계정으로 Docker를 다룸 |
| 전용 서비스 계정 생성 | Docker 전용 계정을 별도로 만들어 그 계정에만 권한 부여 |
| `docker` 그룹 활용 (Linux) | 리눅스에서 Docker 설치 마지막 단계에서 흔히 하는 방식 — `docker`라는 이름의 사용자 계정과 그룹을 만들고, 그 그룹에 Docker 사용 권한을 할당 |

```bash
# 리눅스 예시: docker 그룹에 사용자 추가 (직접 root로 매번 실행하지 않도록)
sudo groupadd docker
sudo usermod -aG docker $USER
```

> Windows/macOS의 Docker Desktop 사용자는 이 부분을 특별히 신경 쓰지 않고 쓰는 경우가 많아, **의식적인 주의가 필요**하다는 점이 강조됨.

## 5. TLS/SSL로 데몬 통신 보호

- Client ↔ Daemon 간, 또는 Daemon ↔ 다른 호스트/컨테이너 간 데이터를 주고받을 때 **TLS를 활성화**해서 통신을 암호화해야 한다.
- **HTTPS**의 구조 복습: `HTTP` (Hypertext Transfer Protocol) + `S` (**Secure**) = 보안이 적용된 프로토콜. 브라우저 주소창의 자물쇠 아이콘이 바로 이 인증서 적용 여부를 나타낸다.
- TLS 인증을 위해 **인증키(인증서)**가 필요하며 두 가지 방식이 있다:
  - **셀프 사인 인증서(Self-signed)**: 자체 생성, 주로 테스트 용도
  - **공인 인증기관(CA) 발급 인증서**: 실제 운영 환경에서 일반적으로 사용
- 인증서를 어디서 발급받았는지, 파일이 어디 있는지, 어느 호스트에 적용할지를 설정한 뒤 그 정보를 바탕으로 Docker Daemon을 기동한다.

## 6. API 접근 제한

- Client의 명령은 Daemon에게 **API 형태**로 전달된다.
- 이 API는 Docker만의 특수한 것이 아니라, 일반적인 서비스 API와 마찬가지로 **접근 제한/인증**이 필요하다.
- **인증된 사용자와 시스템만** Docker API를 호출할 수 있도록 제약을 걸어야, 무단으로 컨테이너를 생성/삭제/조작하는 것을 막을 수 있다.

---

## 7. 핵심 정리 (체크리스트)

- [ ] Docker 보안은 **데몬(엔진) → 이미지 → 컨테이너 격리 → 런타임** 4가지 영역으로 나눠 접근
- [ ] Docker Daemon은 보통 **루트 권한**으로 실행됨 — 이를 인지하고 접근을 제한할 것
- [ ] 가능하면 **루트 계정 직접 사용을 피하고**, 전용 계정/그룹(예: `docker` 그룹)을 활용
- [ ] Windows/macOS Docker Desktop 환경은 리눅스 대비 세밀한 권한 제어가 어려우므로 더 신경 써야 함
- [ ] Client-Daemon 간 통신은 **TLS/SSL**을 활성화해 암호화 (자체 서명 인증서 vs 공인 CA 인증서)
- [ ] Docker의 API도 **인증된 사용자/시스템만 접근 가능**하도록 제한
