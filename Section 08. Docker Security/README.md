# Docker 보안 vs 클라우드 네이티브 애플리케이션 보안

## 1. 클라우드 네이티브 4대 컴포넌트 복습

| 컴포넌트 | 설명 |
|---|---|
| 마이크로서비스 아키텍처 | 하나의 서비스가 아니라 여러 개로 잘게 쪼갠 서비스를 유기적으로 연결 |
| 컨테이너 가상화 기술 | 마이크로서비스를 운영하기 위한 가상화 방식 (Docker 등) |
| CI/CD | 컨테이너화된 결과물을 자유롭게 배포하는 기술 |
| DevOps | 개발·운영이 지속적으로 협업하며 서비스를 개선해나가는 문화 |

Docker는 이 네 가지 중 **컨테이너 가상화 기술**에 해당한다. 이번 학습에서 다루는 "보안"은 이 네 가지 컴포넌트를 아우르는 **클라우드 네이티브 보안**과, 그중 컨테이너 부분만 다루는 **Docker 보안** 두 가지로 나눠서 이해할 필요가 있다.

## 2. Docker 보안 vs 클라우드 네이티브 보안 — 범위 비교

<img width="825" height="636" alt="image" src="https://github.com/user-attachments/assets/d5f5ee95-deee-4e00-81c2-4dc4eead0497" />

| 구분 | 범위 | 주요 관심사 |
|---|---|---|
| **클라우드 네이티브 보안** | 컨테이너, 서버리스, 마이크로서비스 등 **애플리케이션 전체 생명주기** | 멀티/하이브리드 클라우드 데이터 보안, 보안 정책, 서비스 메시(Istio), TLS/SSL, 지속적 모니터링, Kubernetes 오케스트레이션 보안 |
| **Docker(컨테이너) 보안** | **컨테이너 단위**에 국한된 부분집합 | 이미지 취약점, 컨테이너 런타임 보안, 컨테이너 네트워크/격리, 컨테이너 구성 관리 |

즉 Docker 보안은 클라우드 네이티브 보안이라는 큰 우산 안에 속한 **한 조각**이다. 클라우드 환경에서는 서비스를 직접 구축한 팀/회사가 모든 걸 책임지는 게 아니라, **클라우드가 제공하는 보안 기능 + 사용자가 직접 챙겨야 할 보안** 둘 다 필요하다는 점도 기억할 것.

## 3. 멀티 클라우드 / 하이브리드 / 프라이빗 클라우드

| 용어 | 의미 |
|---|---|
| 멀티 클라우드 | 하나가 아니라 **여러 클라우드 벤더**(AWS, GCP, Azure, 네이버클라우드/NCP, NHN 등)를 함께 사용하는 환경 |
| 하이브리드 클라우드 | 여러 환경(퍼블릭+프라이빗 등)에 걸쳐 서비스를 운영하는 형태 |
| 프라이빗 클라우드 | 상용 클라우드 대신 **회사 자체적으로 구축한** 클라우드 환경 (자체 커스터마이징 가능) |

이런 환경에서는 데이터 보안, 보안 정책 적용, 지속적 모니터링이 필수적이다.

## 4. 서비스 메시 (Service Mesh) — Kubernetes + Istio

컨테이너 오케스트레이션이 커지면(Docker Swarm보다 **Kubernetes**가 실무에서 더 일반적으로 쓰임), 서비스 간 통신·보안·라우팅을 관리해주는 **서비스 메시**가 필요해진다. 대표 제품이 **Istio**.

### Inner Architecture vs Outer Architecture

| 구분 | 의미 |
|---|---|
| **Inner Architecture** | 비즈니스 로직, 도메인 지식을 담은 **서비스의 실제 기능**(무엇을 제공할지) |
| **Outer Architecture** | Inner Architecture가 잘 작동하도록 지원하는 **백킹 서비스**: 서비스 등록/삭제(레지스트리), 라우팅, 게이트웨이, 보안 정책, 구성 파일 관리, 스토리지 등 |

Istio는 이 Outer Architecture 영역에서 **서비스 간 TLS 통신, 트래픽 제어, 보안 정책 적용** 등을 담당한다. (예: `DestinationRule` 리소스로 네임스페이스·호스트·트래픽 정책을 지정)

## 5. SSL과 TLS

| 용어 | 풀네임 | 설명 |
|---|---|---|
| **SSL** | Secure Socket Layer | 웹사이트-브라우저 또는 서버 간 전송 데이터를 암호화하는 초기 표준 기술. 해킹, 개인/금융정보 탈취 방지 목적 |
| **TLS** | Transport Layer Security | SSL의 **향상되고 더 안전한 후속 버전** |

> 실무에서는 지금 쓰는 것이 기술적으로 TLS라 하더라도 관용적으로 **"SSL 인증서"**라는 표현을 더 널리 사용한다. "SSL 쓴다"는 말은 사실상 "TLS 쓴다"는 의미로 이해하면 된다.

## 6. Docker 보안이 다루는 구체적인 영역

- **이미지 보안**: 이미지 자체에 알려진 취약점(CVE)이 있는지 점검
- **컨테이너 런타임 보안**: 컨테이너가 실행되는 동안의 보안 설정
- **네트워크/격리**: 컨테이너 간 네트워크 구성, 격리 수준 관리
- **컨테이너 구성 관리**: 불필요한 권한, 설정값 등을 최소화

---

## 7. 핵심 정리 (체크리스트)

- [ ] Docker는 클라우드 네이티브 4대 컴포넌트 중 **컨테이너 가상화 기술**에 해당
- [ ] **클라우드 네이티브 보안**(전체 생명주기, 멀티클라우드, 서비스 메시, 모니터링)과 **Docker 보안**(컨테이너 단위)은 스코프가 다르다 — Docker 보안은 그 부분집합
- [ ] 클라우드 사용 시 클라우드가 제공하는 보안 + 사용자가 직접 챙겨야 하는 보안이 둘 다 필요
- [ ] 서비스 메시(Istio)는 Outer Architecture 영역에서 서비스 간 통신 보안·라우팅·정책을 담당
- [ ] "SSL"이라는 용어는 관용적 표현이며, 실질적으로는 더 발전된 버전인 **TLS**를 의미하는 경우가 많음
