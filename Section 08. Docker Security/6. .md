# Docker 로깅 & 모니터링 개요


## 1. 왜 로깅과 모니터링이 필요한가

- **로깅(Logging)**: 컨테이너에서 발생하는 이벤트/데이터를 기록하는 것
- **모니터링(Monitoring)**: 그 로그를 보기 쉽게 시각화하거나, 판단 가능한 지표로 제시하는 것
- 지속적으로 로그를 유지·관리해야 **보안 사고를 감지**하고 **문제를 신속히 해결**할 수 있다.

---

## 2. ⚠️ 핵심 문제 — 컨테이너 로그는 휘발성이다

- 컨테이너 내부에 로그가 계속 쌓이더라도, **그 컨테이너가 삭제되면 로그도 함께 사라진다.**
- 따라서 로그는 반드시 **컨테이너 외부의 별도 시스템(External System)**에서 관리해야 한다.
- 여러 컨테이너의 로그를 **한 곳에 중앙집중식으로 모아두는 스토리지**를 활용하면, 한 군데에서 통합 관리·분석이 가능해진다.

## 3. syslog로 로그 전달하기

리눅스에서는 시스템 전반의 로그를 **syslog**라는 이름으로 관리하는 것이 일반적이다. Docker 컨테이너의 로그도 이 syslog로 전달하도록 설정할 수 있다.

```bash
docker run \
  --log-driver=syslog \
  --log-opt syslog-address=<syslog 서버 주소> \
  <이미지명>
```

- `--log-driver=syslog`: 로그를 syslog 방식으로 기록하겠다는 옵션
- `--log-opt syslog-address=...`: 로그를 전달할 syslog 서버의 주소를 명시

> 옵션을 지정하지 않으면 기본적으로 **로그는 해당 컨테이너 내부에만** 남는다 — 앞서 말한 휘발성 문제가 그대로 발생.

이 부분(syslog 연동 실습)은 **다음 섹션에서 실제 예제로 진행**될 예정.

## 4. 정기적인 업데이트 & 보안 패치의 중요성

Docker 보안은 한 번 설정해두고 끝나는 것이 아니라 **지속적인 관리**가 필요하다.

- Docker 엔진, 이미지, 컨테이너 전반에 대해 **정기적으로 업데이트** 진행
- 이미지의 보안 취약점을 **주기적으로 재점검** ([`docker-image-security-scan.md`](./docker-image-security-scan.md)의 Docker Scout/Trivy 활용)
- 새로운 취약점이 발견되면 → 이미지 업데이트 → 컨테이너 재배포 순서로 **보안 패치 적용**

## 6. 핵심 정리 (체크리스트)

- [ ] 컨테이너 로그는 **휘발성** — 컨테이너 삭제 시 함께 사라짐을 반드시 인지
- [ ] 로그는 **외부 시스템에 중앙집중식으로 저장**해서 관리 (syslog, 또는 ELK/Fluentd 등 별도 솔루션)
- [ ] `docker run --log-driver=syslog --log-opt syslog-address=<주소>`로 syslog 연동 가능
- [ ] Docker 엔진/이미지/컨테이너는 **정기적으로 업데이트 및 취약점 재점검** 필요
- [ ] 취약점 발견 시 → 이미지 업데이트 → 컨테이너 재배포로 패치 적용하는 사이클을 습관화
