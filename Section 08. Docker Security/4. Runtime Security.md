# Docker 런타임 보안 레퍼런스 (seccomp, Capabilities, Non-root User)

## 1. 런타임 보안이란

지금까지 준비 단계(데몬 → 이미지 → 격리된 네트워크 구성)가 끝났다면, 실제로 컨테이너가 **동작하고 있는 상태(런타임)**에서도 지속적인 보안 강화와 모니터링이 필요하다. 이번 문서에서 다루는 핵심은 **"컨테이너가 실행 중일 때 무엇을 할 수 있고, 무엇을 하지 못하게 막을 것인가"**.

---

## 2. seccomp — 시스템 호출 제한

- **seccomp** = Secure Computing Mode. 애플리케이션이 수행할 수 있는 **시스템 호출(system call)을 제한**하는 리눅스 커널 보안 기능.
- Docker는 seccomp를 이용해 컨테이너가 사용할 수 있는 시스템 호출 범위를 좁혀서, 공격받을 수 있는 표면적(attack surface)을 줄인다.

```bash
docker run --security-opt seccomp=<프로필경로>.json <이미지>
```

- 프로필은 어떤 시스템 호출을 허용/차단할지 정의한 **JSON 파일**.
- 기본 seccomp 프로필에는 Docker 운영에 필요한 최소한의 기능이 이미 포함되어 있으며, 필요에 따라 더 제한적인 커스텀 프로필을 적용할 수 있다.

## 3. Linux Capabilities — 루트 권한을 잘게 쪼개서 제어

### 3.1 왜 필요한가

- 루트(root) 사용자는 운영체제 전반에 대한 **모든 권한**을 갖는다 — 즉 공격자가 루트 권한을 얻으면 사실상 모든 것이 가능해진다는 뜻.
- Linux Capabilities는 이 거대한 "루트 권한"을 **세분화된 개별 기능 단위**로 쪼갠 것이다. 예: `CHOWN`(소유자 변경), `KILL`(프로세스 종료), `SETUID`/`SETGID`(사용자/그룹 ID 설정), 네트워크 관련 권한, 파일시스템 관련 권한 등.
- 기본 상태에서는 이 Capabilities가 대부분 **활성화된 채로 컨테이너가 생성**된다 — 즉 웬만한 설치/설정 작업이 자유롭게 가능하다는 뜻이기도 하다.

### 3.2 제어 옵션

| 옵션 | 설명 |
|---|---|
| `--cap-drop=all` | 모든 Capabilities를 제거 (아무 권한도 없는 상태로 시작) |
| `--cap-add=<권한명>` | 필요한 권한만 다시 추가 (예: `CHOWN`, `SETUID`, `SETGID`) |

> ⚠️ **중요한 제약**: Capabilities는 **컨테이너 생성 시점에만 설정 가능**하다. 일단 컨테이너가 실행된 후에는 다시 활성화할 수 없다 — 다시 켜려면 컨테이너를 **재생성**해야 한다. 이 "한번 정해지면 되돌릴 수 없음" 특성이 오히려 보안을 강화해준다.

### 3.3 빌드 시점 vs 실행 시점의 차이

- **Dockerfile로 이미지를 빌드(build)하는 과정**에서는 어차피 높은 권한으로 빌드가 진행되기 때문에, 이 단계에서 권한을 제약하는 것은 사실상 불가능하다 (예: `apt-get install curl` 같은 명령이 빌드에 필요하면 그대로 실행돼야 함).
- **하지만 빌드가 끝난 이미지를 실제로 실행(run)할 때는 권한을 제약할 수 있다.** 즉 Capabilities 제어는 "이미지를 어떻게 만드느냐"가 아니라 **"만들어진 이미지를 어떤 권한으로 실행하느냐"**의 문제.

```bash
# Dockerfile로 이미지 빌드 (여기서는 권한 제약 불가)
docker build -t my-image .

# 빌드된 이미지를 실행할 때 권한 최소화
docker run --rm -it \
  --cap-drop=all \
  --cap-add=CHOWN --cap-add=SETUID --cap-add=SETGID \
  my-image
```

## 4. 실습: 3단계로 Capabilities 차이 비교

`first:0.1`(단순 Linux 베이스 이미지)로 아래 3단계를 비교해본다.

![Linux Capabilities 제어 3단계 비교](./linux-capabilities-3steps.svg)

### ① 기본 상태 (제약 없음)

```bash
docker run -it first:0.1 bash
apt-get update   # 정상 작동 — 모든 권한을 가진 슈퍼유저 상태
```

### ② 모든 Capabilities 제거

```bash
docker run --rm -it --cap-drop=all first:0.1 bash
apt-get update   # 실패 — "권한이 없습니다" 류의 오류 발생
```

### ③ 필요한 최소 권한만 재추가

```bash
docker run --rm -it \
  --cap-drop=all \
  --cap-add=CHOWN --cap-add=SETUID --cap-add=SETGID \
  first:0.1 bash

apt-get update   # 다시 정상 작동 — 필요한 최소 권한만으로도 충분
```

**결론**: 전체 허용(①)도, 전체 차단(②)도 정답이 아니다. **필요한 최소 권한만 선별해서 부여(③)**하는 것이 보안과 기능 사이의 균형점.

## 5. Dockerfile에서 비루트(non-root) 사용자로 실행하기

Dockerfile의 `USER` 명령어를 이용하면, 컨테이너 내부의 프로세스를 **루트가 아닌 별도 계정**으로 실행하게 만들 수 있다.

```dockerfile
FROM ubuntu:latest

RUN adduser -D non-root-user   # 비루트 계정 생성
USER non-root-user             # 이후 명령/프로세스는 이 계정 권한으로 실행

# 이후 CMD, ENTRYPOINT 등도 non-root-user 권한으로 동작
```

### `adduser` vs `useradd` 차이

| 명령어 | 특징 |
|---|---|
| `adduser` | 계정 생성 시 **홈 디렉토리를 자동으로 함께 생성** — 더 간편 |
| `useradd` | 홈 디렉토리를 자동 생성하지 않음 (`-d` 옵션 등으로 별도 지정 필요) |

> 간편하게 쓰려면 `adduser`(또는 `-d` 옵션과 함께 쓰는 `useradd -d`)가 편리하다.

## 6. 핵심 정리 (체크리스트)

- [ ] **seccomp**로 컨테이너가 사용할 수 있는 시스템 호출 자체를 제한 (`--security-opt seccomp=<profile>.json`)
- [ ] **Linux Capabilities**로 루트 권한을 세분화해서 제어: `--cap-drop=all` + 필요한 것만 `--cap-add`
- [ ] Capabilities는 컨테이너 **생성 시점에만** 설정 가능 — 실행 중 재변경 불가(재생성 필요)
- [ ] 이미지 **빌드 시점**에는 권한 제약이 어렵고, **실행(run) 시점**에 제약을 거는 것이 현실적인 접근
- [ ] Dockerfile에서 `USER` 지시자로 **비루트 계정** 지정 → 컨테이너 프로세스를 낮은 권한으로 실행
- [ ] 계정 생성 시 `adduser`가 `useradd`보다 홈 디렉토리 자동 생성 등 더 간편
