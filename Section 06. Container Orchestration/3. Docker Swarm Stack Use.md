# Docker Stack 실습 레퍼런스 (HAProxy + Nginx, 오버레이 네트워크)

---

## 1. Stack이 필요한 이유 (Compose → Service → Stack 흐름 복습)

| 도구 | 관리 단위 | 한계 |
|---|---|---|
| Docker Compose | 여러 컨테이너를 하나의 파일로 | **단일 호스트**에서만 가능 |
| Docker Service | 여러 호스트에 걸쳐 컨테이너 묶음 배포 | 이미지(서비스) **1개만** 운영 가능 |
| **Docker Stack** | 여러 **Service**를 묶어서 배포 | Compose 스타일 파일로 멀티 서비스 · 멀티 호스트 모두 지원 |

즉 Stack = "Docker Compose 스타일 파일 + 멀티 호스트(Swarm) 배포"의 조합.

---

## 2. 오버레이(Overlay) 네트워크

| 드라이버 | 범위 | 설명 |
|---|---|---|
| bridge | 단일 호스트 | 기본값. 통신 시 반드시 호스트 PC 네트워크를 거침 |
| host | 단일 호스트 | 호스트 PC와 동일한 네트워크 사용 |
| none | - | 네트워크 미사용 |
| **overlay** | **멀티 호스트** | Swarm 전용. 여러 호스트(노드)에 흩어진 컨테이너를 **같은 네트워크에 있는 것처럼** 통신시켜줌 |

Stack을 배포하려면 사용할 overlay 네트워크가 **미리 생성되어 있어야** 한다 (Stack이 자동 생성해주지 않음).

```bash
# 매니저 노드에서 실행
docker network create --driver overlay my-overlay-network

# 확인
docker network ls
```

> 기본적으로 Swarm 초기화 시 `ingress`라는 오버레이 네트워크가 자동 생성되지만, 서비스 간 통신용으로는 별도 이름(`my-overlay-network`)의 네트워크를 직접 만들어 쓰는 것이 일반적.

## 3. Stack 명령어 레퍼런스

| 명령어 | 설명 |
|---|---|
| `docker stack deploy -c <compose파일> <스택이름>` | Compose 스타일 yaml로 스택 배포 |
| `docker stack ls` | 배포된 스택 목록 |
| `docker stack services <스택이름>` | 스택에 속한 서비스들의 상태(replica 등) 확인 |
| `docker stack ps <스택이름>` | 스택의 개별 컨테이너들이 **어느 노드**에 배포됐는지 상세 확인 |
| `docker stack rm <스택이름>` | 스택 삭제 (관련 서비스·컨테이너 모두 정리) |

```bash
docker stack deploy -c stack/stack-sample.yaml mystack
docker stack ls
docker stack services mystack
docker stack ps mystack
docker stack rm mystack
```

## 4. 아키텍처 개요 (이번 실습 구성)

<img width="809" height="486" alt="image" src="https://github.com/user-attachments/assets/905027d6-c02c-41ad-8fef-520e05204d95" />

- **nginx**: replica 2개, `role == worker` 조건으로 **워커 노드에만** 배포 (매니저 제외)
- **haproxy**: **매니저 노드에만** 배포. Nginx 앞단에서 로드밸런서/게이트웨이 역할
- 사용자는 항상 `HAProxy`가 열어놓은 포트 하나로만 접속하고, HAProxy가 내부적으로 nginx 두 대 중 하나로 요청을 라운드 로빈 전달
- 모든 서비스는 `my-overlay-network`로 묶여있음

## 5. stack-sample.yaml 재구성 예시

```yaml
version: "3.8"

services:
  nginx:
    image: nginx:latest
    deploy:
      replicas: 2
      placement:
        constraints:
          - node.role == worker      # 매니저 제외, 워커에만 배포
    networks:
      - my-overlay-network

  haproxy:
    image: haproxy:latest
    volumes:
      - ./haproxy.cfg:/usr/local/etc/haproxy/haproxy.cfg   # 커스텀 설정 마운트
    ports:
      - "8000:80"                     # 호스트:컨테이너 (호스트 포트는 환경마다 조정)
    deploy:
      placement:
        constraints:
          - node.role == manager      # 매니저 노드에만 배포
    networks:
      - my-overlay-network

networks:
  my-overlay-network:
    external: true                    # 사전에 생성해둔 오버레이 네트워크 사용
```

> **Windows 11 환경 실습에서는** 매니저 노드가 `80` 포트를 서비스하고, 이를 호스트에서 `8081:80`으로 매핑해서 사용했다 (macOS 예시는 `8000:80`). **본인이 매니저 노드를 기동할 때 어떤 호스트 포트로 매핑했는지에 따라 웹브라우저 접속 포트가 달라진다** — 반드시 본인 환경의 Compose 파일 설정을 확인할 것.

## 6. haproxy.cfg — 두 가지 백엔드 등록 방식

### 방법 A — 정적 IP 하드코딩 (문제가 있는 방식)

```
backend nginx_backend
    balance roundrobin
    server app1 10.0.1.28:80 check
    server app2 10.0.1.29:80 check
```

- Nginx 컨테이너가 실제로 배포된 뒤 얻는 **오버레이 네트워크 IP**를 알아내서(`docker inspect <컨테이너ID>`) 직접 써넣어야 한다.
- **문제점**: 스택을 재배포하면 IP가 매번 바뀐다. 그때마다 `haproxy.cfg`를 수정하고 `docker service update --force <스택>_haproxy`로 강제 재기동해야 함 → 최초 배포 시 `503 Service Unavailable` 발생 (HAProxy가 아직 Nginx IP를 모르는 상태)

```bash
# nginx 컨테이너의 실제 IP 확인
docker inspect <nginx 컨테이너ID>   # NetworkSettings > Networks > my-overlay-network > IPAddress

# haproxy.cfg 수정 후, 실행 중인 서비스에 강제 반영
docker service update --force mystack_haproxy
```

### 방법 B — server-template + DNS Resolver (권장하는 방식)

```
resolvers docker
    nameserver dns1 127.0.0.11:53

backend nginx_backend
    balance roundrobin
    server-template app 2 nginx:80 check resolvers docker init-addr none
```

- `nginx`는 Compose 파일에서 정의한 **서비스명**. Docker Swarm은 컨테이너 기동 시 기본 DNS(`127.0.0.11:53`)를 통해 서비스명 → 실제 IP를 자동으로 알려준다.
- `server-template app 2 nginx:80`: `app1`, `app2`라는 이름으로 2개까지 자동 확장 등록, 실제 IP는 DNS로 매번 동적으로 조회.
- **장점**: 스택을 몇 번을 재배포해도 IP를 수동으로 갱신할 필요가 없다. 실무에서는 이 방식을 사용하는 게 일반적.

## 7. 전체 실행 순서 (macOS 기준 실습 로그 재구성)

```bash
# 0) (재실습 시) 기존 컨테이너/Swarm 정리
docker swarm leave --force      # 각 노드에서, 아직 클러스터에 속해있다면
docker stop manager worker1 worker2
docker rm manager worker1 worker2

# 1) DinD 3개 노드를 한번에 기동 (개별 docker run 대신 Compose 사용 — 훨씬 간편)
docker-compose -f docker-compose-macos.yaml up --detach
docker-compose -f docker-compose-macos.yaml ps

# 2) 각 노드에서 내부 Docker 데몬 기동
docker exec -it manager bash  -c "systemctl start docker"
docker exec -it worker1 bash  -c "systemctl start docker"
docker exec -it worker2 bash  -c "systemctl start docker"

# 3) Swarm 클러스터 구성
docker exec -it manager bash
docker swarm init                          # 토큰 발급
# → 워커 노드들에서 (각각)
docker swarm join --token <TOKEN> <MANAGER_IP>:2377

# 4) 매니저에서 클러스터 확인
docker node ls                             # Leader + Worker 2개 확인

# 5) 오버레이 네트워크 생성 (필수, Stack이 자동 생성 안 해줌)
docker network create --driver overlay my-overlay-network

# 6) 스택 배포 (stack 폴더는 볼륨 마운트로 이미 매니저 컨테이너 내부에 있음)
cd /stack
docker stack deploy -c stack-sample.yaml mystack

# 7) 상태 확인
docker stack services mystack
docker stack ps mystack

# 8) 브라우저 확인
# macOS 예시: http://localhost:8000
# Windows 예시: http://localhost:8081

# 9) HAProxy 통계 페이지 확인
# http://localhost:8000/haproxy?stats
```

## 8. OS별 환경 차이 (macOS / Windows 10 / Windows 11)

DinD 방식으로 노드를 띄울 때, 강의에서 제공하는 GitHub 저장소의 **`section-5` 브랜치**에 OS별 Docker Compose 파일이 미리 준비되어 있다. 셋 다 하는 작업 자체는 동일하지만 아래 2가지가 다르므로 반드시 본인 환경에 맞는 파일을 확인해야 한다.

```bash
git checkout section-5     # 실습용 브랜치로 전환
```

| 항목 | macOS | Windows 10 | Windows 11 |
|---|---|---|---|
| 사용할 Compose 파일 | `docker-compose-macos.yaml` | `docker-compose-win10.yaml` | `docker-compose-win11.yaml` |
| DinD 이미지 태그 | `m1` (Apple Silicon) / intel용 별도 태그 | `docker:latest` | `docker:no_iptables` |
| 매니저 컨테이너 외부 포트(HAProxy 접속용) | `8000:80` | 환경에 따라 상이 (Compose 파일 확인) | `8081:80` |
| 웹브라우저 접속 주소 | `http://localhost:8000` | Compose 파일에 매핑된 포트로 | `http://localhost:8081` |

> Windows 11에서 `docker:latest` 태그를 그대로 쓰면 iptables 관련 오류가 발생해서, 강의에서는 별도로 **`no_iptables`** 태그의 이미지를 만들어 배포했다. Windows 10은 기존 `latest` 태그로 정상 작동.

### Windows 11 기준 전체 명령어 시퀀스 (macOS와 흐름은 동일, 이미지/포트만 다름)

```powershell
# 1) 저장소에서 section-5 브랜치의 docker-compose-win11.yaml 사용
docker-compose -f docker-compose-win11.yaml up --detach
docker-compose -f docker-compose-win11.yaml ps      # manager, worker1, worker2 확인

# 2) 각 노드 내부 Docker 데몬 기동 (exec로 접속 후 실행)
docker exec -it manager bash
systemctl start docker
exit

docker exec -it worker1 bash
systemctl start docker
exit

docker exec -it worker2 bash
systemctl start docker
exit

# 3) Swarm 클러스터 구성
docker exec -it manager bash
docker swarm init                       # 토큰 발급

# 워커 노드들에서 각각 (매니저에서 복사한 join 명령 그대로 실행)
docker exec -it worker1 bash
docker swarm join --token <TOKEN> <MANAGER_IP>:2377
exit

docker exec -it worker2 bash
docker swarm join --token <TOKEN> <MANAGER_IP>:2377
exit

# 4) 매니저에서 확인
docker exec -it manager bash
docker node ls                          # Leader(manager) + worker1 + worker2 확인

# 5) 스택 배포 전 오버레이 네트워크 생성 (기존에 없으면 에러 발생 → 이후 생성)
docker network create --driver overlay my-overlay-network

# 6) 볼륨 마운트된 stack 폴더로 이동 후 배포
cd /stack
docker stack deploy -c stack-sample.yaml mystack

# 7) 상태 확인
docker stack services mystack
docker stack ps mystack          # nginx 2개 + haproxy 1개, 각각 어느 노드인지 확인
```

**브라우저 확인**: `http://localhost:8081` (macOS는 `8000`)

**정리**:
```bash
docker stack rm mystack
```

> Windows 10을 사용한다면 위 시퀀스는 완전히 동일하되, 1번 단계의 Compose 파일만 `docker-compose-win10.yaml`로 바꾸고, 접속 포트도 해당 파일에 지정된 값으로 확인해서 사용하면 된다.

## 9. 트러블슈팅 체크리스트

| 증상 | 원인 | 해결 |
|---|---|---|
| `network my-overlay-network not found` | Stack 배포 전 오버레이 네트워크 미생성 | `docker network create --driver overlay my-overlay-network` 실행 후 재배포 |
| `503 Service Unavailable` | HAProxy가 Nginx의 실제 IP를 모름 (정적 IP 방식 사용 시 배포 전이라 값이 비어있음) | 방법 A라면 IP 확인 후 cfg 수정 + `service update --force`, 근본 해결은 방법 B(DNS resolver)로 전환 |
| `docker-compose` 실행 시 `no configuration file provided` | 기본 파일명(`docker-compose.yaml`)이 아닌 파일 사용 중 | `-f <파일명>` 옵션으로 명시적으로 지정 |
| SSH로 컨테이너 접속 안 됨 | Compose 파일에 SSH 포트(22)가 매핑 안 되어 있음 | Compose 파일에 `- "10022:22"` 같은 포트 매핑 추가, 또는 `docker exec -it <이름> bash`로 대체 |
| 이전 Swarm 클러스터가 남아있어 새 클러스터 구성이 꼬임 | 이전 실습에서 `swarm leave`를 안 하고 컨테이너만 삭제 | 각 노드에서 `docker swarm leave --force` 후 컨테이너 재생성 |
| `clear` 명령어 안 먹힘 (컨테이너 초기 상태) | 베이스 이미지에 `ncurses` 미포함 | `yum install ncurses` (CentOS 계열 DinD 이미지 기준) |
| Windows에서 웹 접속 안 됨 | 매니저 컨테이너의 호스트 포트가 macOS 예시(8000)와 다름(8081) | 본인 Compose 파일에서 실제 매핑된 호스트 포트로 접속 |

## 10. 핵심 정리 (체크리스트)

- [ ] Stack = 여러 Service를 Compose 스타일 yaml로 묶어 배포하는 단위
- [ ] Stack 배포 전 **오버레이 네트워크를 반드시 먼저 생성**
- [ ] `deploy.placement.constraints`로 특정 역할(worker/manager)에만 배포되도록 지정 가능
- [ ] IP를 직접 하드코딩하는 방식은 재배포마다 깨짐 → **DNS resolver + server-template 방식을 기본으로 사용**
- [ ] Windows/macOS는 DinD 이미지 태그와 호스트 포트 매핑이 다르므로, 본인 환경의 Compose 파일을 반드시 확인
- [ ] 정리할 때는 `docker stack rm <이름>` → 필요하면 `docker swarm leave --force`까지
