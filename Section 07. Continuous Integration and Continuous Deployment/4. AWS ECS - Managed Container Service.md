# AWS ECS 실습 — 클러스터 → 태스크 정의 → 서비스(+ALB) 배포

---

## 1. ECS 관리형 서비스란

**Managed(관리형)** = 직접 설치/생성하는 게 아니라 AWS가 이미 구축해놓은 것을 가져다 쓰는 방식. ECS를 쓰면 Docker 런타임 설치, 컨테이너 생성, 버전업 시 기존 컨테이너 삭제 후 새 컨테이너 기동 같은 작업을 AWS가 관리형으로 대신 처리한다.

ECS 사용은 크게 **4단계**로 이루어진다.

| 단계 | 내용 |
|---|---|
| ① Cluster | ECS가 작업할 공간(작업 영역) 생성 |
| ② Task Definition | 어떤 컨테이너 이미지를 쓸지, 리소스는 얼마나 할당할지 등을 정의 |
| ③ Task 또는 Service 생성 | 정의된 태스크를 실제로 실행 (단발성=Task, 지속 운영=Service) |
| ④ (필요 시) Load Balancer 연동 | 여러 태스크를 하나의 진입점으로 묶어 부하 분산 |

프론트엔드/백엔드/DB 등을 서로 다른 조합으로 ECS에 구성해서 운영하는 것도 가능하다.

## 2. 인프라 타입: Fargate vs EC2

| 구분 | Fargate | EC2 |
|---|---|---|
| 서버 관리 | **서버리스** — 사용자가 서버를 직접 준비/관리하지 않음 (내부적으로는 AWS가 서버를 씀) | 사용자가 직접 EC2 인스턴스(VM)를 만들고 그 위에 Docker 설치 |
| 네트워크 | **AWS VPC 타입 고정** | 제약 없이 자유롭게 네트워크 구성 가능 |
| 적합한 경우 | 간단한 서비스를 빠르게 띄울 때 | 자체 관리형 인프라를 세밀하게 구축하고 싶을 때 |
| 과금 | 사용한 리소스만큼 | 리소스 기반(인스턴스 실행 시간 등) |

이번 실습은 **Fargate**로 진행.

## 3. 실습 단계

### 3.1 클러스터 생성

1. AWS 콘솔 검색 → **ECS** 이동
2. **클러스터 생성**
3. 클러스터 이름 입력 (예: `DevCluster`)
4. 인프라: **AWS Fargate (서버리스)** 선택
5. 모니터링/암호화/태그는 선택사항 → 스킵하고 **생성**
6. 생성 완료까지 약 1분 미만 대기

### 3.2 태스크 정의(Task Definition)

1. 왼쪽 메뉴 **태스크 정의** → **새 태스크 정의 생성**
2. 태스크 이름 입력 (예: `cicd-web-project-task`)
3. 시작 유형: **Fargate**
4. 운영체제/아키텍처: **Linux/X86_64**
5. 네트워크 모드: Fargate 선택 시 **AWS VPC 고정**
6. CPU/메모리: 기본값 사용
7. Task 역할: **ECS Task Execution Role** (기본으로 제공되는 유일한 옵션)
8. **컨테이너 설정** (핵심):
   - 컨테이너 이름: 예 `cicd-web-project`
   - 컨테이너 이미지 URI: **ECR에서 직접 선택** → Private Registry → 이전에 만든 레포지토리 → `latest` 태그 선택 → 자동으로 전체 ECR 경로가 채워짐
     - 형식: `<계정ID>.dkr.ecr.<리전>.amazonaws.com/<레포지토리명>:latest`
   - 포트 매핑: 컨테이너가 서비스하는 포트 입력 (예제 이미지는 톰캣 기반이라 **8080**)
9. 리소스 제약, 환경 변수 등은 필요 시 추가 → **생성**

### 3.3 서비스 생성 (클러스터에서 태스크 실행)

1. 생성한 클러스터(`DevCluster`) 선택 → **서비스** 탭 → **생성**
2. 애플리케이션 구성: **서비스** 선택 (웹앱은 보통 Service, 단발성 배치는 Task)
3. **패밀리**: 3.2에서 만든 태스크 정의 선택 (버전은 자동으로 `1`)
4. 서비스 이름 입력 (예: `myecs-service-new`)
5. **태스크 개수**: `2` (로드밸런서 테스트를 위해 2개로 설정)
6. 네트워킹: 사용할 VPC 선택, 서브넷은 가용영역 A/B/C 전부 선택 (여러 개 선택 시 태스크가 자동 분산 배치됨)
7. 보안 그룹: 기본(default) 보안 그룹 사용
8. **로드밸런싱**: 태스크가 2개 이상이면 반드시 필요 (아래 3.4 참고)
9. **생성** 클릭 → 서비스+로드밸런서까지 연결되는 데 3~5분 정도 소요될 수 있음

### 3.4 Application Load Balancer(ALB) 설정 이유와 구성

- Task가 2개라는 것은 컨테이너(예: 톰캣 서버)가 2대 떠 있다는 뜻 → 각각 고유 IP를 가짐
- IP가 동적으로 계속 바뀌므로 사용자가 IP를 직접 기억해서 접속하는 건 비현실적
- **ALB를 앞단에 두면 사용자는 ALB 주소 하나만 알면 되고, 내부적으로 두 Task에 자동 분산**된다

설정 값:

| 항목 | 값 |
|---|---|
| 로드밸런서 종류 | 새로 생성 → **Application Load Balancer** |
| 로드밸런서 이름 | 예: `MyALB` |
| 리스너 포트 | **80** (사용자가 접속하는 포트) → 컨테이너 포트 **8080**에 매핑 |
| 대상 그룹 | 기본값 사용 (자동으로 `ECS-DevCluster-<서비스명>` 형태로 생성됨) |

## 4. 배포 확인

### 4.1 개별 Task로 직접 확인 (테스트용)

1. 서비스 → 태스크 탭에서 Task 1개 클릭
2. **네트워크 바인딩** 탭 → 외부 링크(IP:8080) 확인
3. 브라우저에서 `http://<Task IP>:8080/hello-world` 접속 → 정상 응답 확인

### 4.2 ALB를 통한 실제 서비스 확인 (운영 방식)

1. EC2 콘솔 → **로드밸런싱 → 로드밸런서** → `MyALB` 선택
2. **DNS 이름** 확인 (예: `myalb-xxxxxxx.us-east-1.elb.amazonaws.com`)
3. 브라우저에서 `http://<ALB DNS 이름>/hello-world` 접속 (포트 생략 → 기본 80 사용)
4. 요청할 때마다 Task 1 또는 Task 2 중 하나가 응답 — 사용자는 어느 쪽인지 몰라도 정상 작동

> 배포 도중 일시적으로 "디플로이 실패 후 자동 복구"되는 경우가 있을 수 있는데, 별도 조치 없이도 ECS가 자동으로 재시도/복구하는 경우가 흔하다.

## 5. 핵심 정리 (체크리스트)

- [ ] ECS 사용 순서: **Cluster → Task Definition → Service(+ALB)**
- [ ] Fargate = 서버리스(간단한 서비스에 적합) vs EC2 = 직접 VM 관리(세밀한 제어 가능)
- [ ] Task Definition에서 **ECR 이미지 URI**와 **컨테이너 포트**를 정확히 지정해야 함
- [ ] Task 개수를 2개 이상으로 하면 각기 다른 IP를 가지므로, **ALB로 단일 진입점**을 만들어 부하 분산
- [ ] ALB 리스너 포트(80) → 컨테이너 포트(예: 8080) 매핑, 대상 그룹은 기본값으로 자동 연결
- [ ] 배포 확인은 개별 Task IP로 먼저 테스트 → 최종적으로는 ALB DNS 이름으로 접속해서 확인
